## 1. Six packages, not eleven

**Question.** The plan names eleven distributions. Five of them (`pqx-calendar`, `pqx-plan`,
`pqx-report`, `pqx-staging`, `pqx-pipeline`) have no code yet. Create them empty now?

| Option | Pros | Cons |
| --- | --- | --- |
| **Six — only those receiving code** | Nothing speculative; the coding standards forbid adding config the request did not ask for | The workspace does not yet look like the target diagram |
| Eleven, five empty | Layout matches the plan immediately | Five packages with a `pyproject.toml`, a `py.typed` and an empty `__init__.py` that do nothing; each is churn to review twice |

**Decided: six.** An empty package is a claim about a design that three Phase 0 gates can
still invalidate — if gate 0d cuts `balanced`, `pqx-plan` is a different shape. Each later
phase creates its own. `export-pipeline-spec.md` now says so.

## 2. Shared fixtures via a pytest entry point

**Question.** Six test directories need the same two fixtures. How do they get them?

| Option | Pros | Cons |
| --- | --- | --- |
| **`pytest11` entry point in `pqx-testing`** | Loads wherever pytest runs, root or package; one definition | A layer of indirection someone has to know about |
| `pytest_plugins` in each conftest | Explicit at each site | **Does not work** — pytest refuses `pytest_plugins` in a non-root conftest |
| Copy the fixtures into six conftests | No indirection | Six copies that drift |

**Decided: entry point.** The second option is not merely worse, it is an error. Verified:
`cd packages/pqx-frame && uv run pytest` collects 286 tests with fixtures available.

```toml
[project.entry-points.pytest11]
pqx_testing = "pqx_testing.plugin"
```

## 4. Per-package `tests/` are directories, not packages

**Question.** Should `packages/*/tests/` get `__init__.py`?

**Decided: no.** Pytest's rootdir-relative import gives each module a unique name already.
Adding markers would put twenty test modules back into one namespace — the exact collision
the root `tests/__init__.py` exists to prevent. That root marker stays, with its docstring
rewritten to say why.

## 5. Fixture output moved out of the source tree

**Question.** `DATA_DIR` was `Path(__file__).parent / "data"`. After the move that is inside
`src/pqx_testing/`.

**Decided:** `packages/pqx-testing/data/`, resolved as `parents[2]`, with a `PQX_FIXTURE_DIR`
override. Generated 1000-row workbooks must not sit inside an importable package. The
override exists because `parents[2]` is only right for an editable workspace install.

**Got this wrong once:** the first attempt used `parents[3]`, which is `packages/`, and
created `packages/data/` — which then matched the `packages/*` workspace glob and broke
`uv sync` with "missing a pyproject.toml". Caught immediately; worth knowing the failure mode.

## 6. Dependencies are per-package, derived from imports

**Question.** Give each package the old union, or only what it imports?

**Decided: only what it imports**, read off the actual import statements. Carrying the union
would defeat the split — `pqx-common` would pull in `polars` and `fastexcel` to provide
`zpath`. Consequence: `pqx-frame` declares `universal-pathlib` directly rather than depending
on `pqx-common`, because it uses `UPath` only as a type and does not import `pqx_common`.

## 7. Virtual workspace root

**Decided:** the root `pyproject.toml` has `[tool.uv.workspace]` and no `[project]`. It holds

coverage gate. `uv sync --all-packages` is what installs members, and CI now passes it.

## 11. Two defects the Codex review caught, and one it understated

Both reproduced in isolated environments before being fixed, and both are invisible to a
full `uv sync --all-packages` — which is exactly why CI would not have caught them.

**`pqx-testing` did not declare what its plugin imports.** `pqx_testing.plugin` imports
`pytest` and `structlog` at module level, and loads through a `pytest11` entry point, so it
runs *before collection*. Reproduced: a venv with only `pqx-testing` installed fails with
`ModuleNotFoundError: No module named 'pytest'`. Both are now runtime dependencies of that
package, not dev-only, because a plugin that cannot import is not optional.

**Five packages' tests imported undeclared siblings.** The review named `pqx-frame`; it is
also `pqx-excel`, `pqx-sidecar`, `pqx-verify` and `pqx-testing`. Fixed with a
`[dependency-groups] dev` per package rather than by widening `[project] dependencies`:
`pqx_frame`'s *library* does not import `pqx_common`, only its tests do, and promoting that
to a runtime dependency would make every consumer install it.

Verified after the fix: an environment built only from `packages/pqx-excel/pyproject.toml`
runs its 60 tests, where before it failed at collection.

**The cycle this exposed.** `pqx-testing`'s own `test_fixtures.py` imports `pqx_frame`, while
`pqx-frame` needs `pqx-testing` for fixtures — a dev-dependency cycle. Rather than rely on
uv tolerating it, the test moved to `tests/test_fixtures.py` at the root, which is where it
belongs anyway: it checks the generator's output against `pqx_frame`'s dtype vocabulary, so
it is cross-package by definition. `packages/pqx-testing/tests/` no longer exists.
