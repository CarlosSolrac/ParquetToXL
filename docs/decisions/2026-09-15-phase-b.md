# Phase B — `pqx-calendar`

Date-column interpretation, period keys, period labels and calendar grids, built as a
separately installable package depending on nothing but Pydantic and the timezone database.

**What shipped:** 8 modules, 286 tests, 100% statement and branch coverage on the package with
no partial branches, green under pyright strict, mypy strict, the declaration checker and
pre-commit. Workspace total is 797 tests at 100%, up from 511.

Thirteen questions were decided without asking. Each is recorded below with the alternatives
and why the chosen one won, so a later reader can reopen one without re-deriving the rest.

---

## The questions

### 1. Where do the `date_columns` models live?

`ExportConfig` is Phase C's, in `pqx-plan`, and it is the thing that *contains* `date_columns`.

| Option | Consequence |
| --- | --- |
| In `pqx-plan` with the rest of the configuration | Decoding would have to import the planner. The dependency diagram runs `pqx-calendar -> pqx-plan`; this reverses it. |
| **In `pqx-calendar`, embedded by `ExportConfig` (chosen)** | The arrow stays as drawn. Phase C annotates a field with `DateColumn` and inherits every refusal already tested here. |
| Duplicated in both | Two statements of one rule, guaranteed to drift. |

**Chosen: `pqx-calendar`.** The models and the code that interprets them are one concern; the
package boundary was drawn around exactly that. `pqx-plan` gains a dependency it already has.

### 2. How is month precision represented?

`YYMM` and `YYYYMM` locate a month and nothing finer. `partitioning-spec.md`: *"Do not invent a day."*

| Option | Consequence |
| --- | --- |
| `datetime.date` with day 1, precision recorded beside it | The two travel separately and only one gets checked. A month-precision value reaching a `year-month-day` partitioner as a plain date puts every row of March into "March 1st" with nothing raising. |
| **`CalendarPoint(year, month, day \| None)` (chosen)** | Precision is intrinsic. The daily grid asks for `day`, finds `None`, and refuses. |

**Chosen: `day: int \| None` on the value itself.** The refusal then cannot be forgotten,
because it is not a separate check — it is the absence of the field the caller needs.

### 3. Pydantic models or frozen dataclasses for the value objects?

**Chosen: both, split by origin.** `columns.py` is Pydantic — those models are parsed from
JSON, carry a discriminator, and must mirror the JSON Schema. `CalendarPoint`, `PeriodKey`,
`UndatedBucket` and `CoverageSpan` are frozen slotted dataclasses — computed once per source
row in Phase E's hot path, never parsed, with no use for aliases or schema generation.
Validation still happens, in `__post_init__`, so an invalid instance cannot be constructed.

### 4. Does this package vectorise, or stay scalar?

Phase E reads Parquet with Polars. Decoding forty million values one at a time in Python is slow.

| Option | Consequence |
| --- | --- |
| Polars expression builders here | Contradicts "pure" — the one property that makes this package separable — and pulls Polars into a layer the diagram puts below `pqx-plan`. |
| **Scalar now; a Polars expression builder added here in Phase E (chosen)** | Keeps the layer pure today. The golden matrix is scalar anyway: window boundaries and leading zeros are per-value rules. |
| Scalar here, vectorised separately in `pqx-pipeline` | Two implementations of the century window in two packages, and only one of them has this test matrix. |

**Chosen: scalar now, vectorised later in this same package.** ⚠️ **This is the one decision
with a live risk attached.** When Phase E adds the fast path, it must land *here*, beside the
scalar one, with a property test asserting the two agree across the whole fixture — not in
`pqx-pipeline`. A second decoder in another package would be a second century-window rule.

### 5. How does `Undated` end up last under *both* orderings?

The spec: *"placed last regardless of `period_order`"*.

A sort key ranking `Undated` high puts it **first** under `descending` — the one arrangement
forbidden. **Chosen:** `order_buckets()` sorts the dated keys and *appends* the undated bucket,
so the rule is structural rather than a matter of getting a comparator right. This is why
ordering is a function rather than a `sorted()` call at each call site.

### 6. `Undated` as a sentinel type, or as `None`?

**Chosen: a distinct `UndatedBucket` type, with the singleton `UNDATED`.** With `None`, a
bucket variable is also the "no bucket yet" value, and a forgotten null check surfaces where a
sheet named `None` reaches Excel rather than at the type checker.

### 7. How does a decode error learn the column name and the row ordinal?

The spec requires errors naming the column, the row ordinal and the value. The decoder knows
only the value: the name lives in the source's `date_columns` mapping, and the ordinal exists
only while a frame is being scanned.

| Option | Consequence |
| --- | --- |
| Optional `column_name` / `row_ordinal` parameters with `None` defaults | A caller can forget the half of the message that makes it actionable in a 40M-row file. |
| **Bare raise, enriched by `decode_cell(..., *, column_name, row_ordinal)` (chosen)** | Required keyword arguments on the entry point Phase E calls. Unit tests of the primitives stay clean. |

**Chosen: enrichment at the boundary, via `DateDecodeError.located()`**, which returns a new
instance rather than mutating — the bare error may already be an `except` clause's argument
further up, and rewriting its message underneath that handler changes what a log line said
after it was written. `UnknownTimezoneError` is deliberately *not* located: it is a property
of the column and the machine, and locating it would print the same line once per million rows.

### 8. Are years zero-padded in labels?

Every year in the spec's tables is four digits, so the tables do not answer this. `MIN_YEAR` is 1.

**Chosen: `{year:04d}`.** Identical to the tables for any realistic year, and year 5 renders
`0005` rather than `5`, which is the difference between sorting before and after `1999` in a
directory listing. Invisible where the spec looks, correct where it does not.

### 9. Does `DateColumnBase` declare `type: str`?

The spec's snippet shows `IntDateColumn(DateColumnBase, frozen=True)` but not the base's body.

**Chosen: the base declares no `type` field.** A base declaring `type: str` makes each
member's `Literal` an incompatible override of a mutable attribute — pyright strict rejects it —
and the discriminator has to be the narrow literal on the member for the union to resolve.

### 10. When is an unknown IANA zone refused?

| Option | Consequence |
| --- | --- |
| At configuration-parse time | A configuration read on a machine with older `tzdata` than the one that will run the export is rejected for a zone the exporter could honour. |
| **At first use (chosen)** | The machine that has to resolve the zone is the one that complains. |

**Chosen: first use**, raising `UnknownTimezoneError` — a distinct type from `DateDecodeError`,
because "this machine lacks a zone" and "this row holds a bad value" want different responses.

### 11. Month abbreviations from `strftime("%b")` or a fixed table?

**Chosen: a hardcoded English tuple.** `%b` reads the computer's locale, so the same export
yields `Sep` on one machine and `sept.` on another — which changes a filename, and therefore
changes whether a re-run overwrites the previous run's output or sits beside it.

### 12. Where does `year_split_months` ordering get checked?

The JSON Schema constrains member values and uniqueness; strict descent and the terminal `1`
are semantic. **Chosen: `validate_year_split_months()` in `pqx-calendar`**, beside the grids it
governs. A test enumerates all sixteen valid arrays — the descending subsets of `{6,4,3,2}`
followed by `1` — so the validator is proved to accept the whole set, not an arbitrary subset.

### 13. Is `require_base_period_supported` routed through `column_precision`?

**Chosen: no — it tests `isinstance(column, IntDateColumn)` directly.** Only an integer column
can carry month precision, so routing through the helper leaves a branch for "a `date` column
with month precision" that no input can reach, and an uncoverable branch under a 100% gate is a
branch someone eventually disables the gate for.

## Two things the spec did not settle, now settled

- **`resolve_two_digit_year(99, 1970)` is 1999, not 2099.** A first draft of the test asserted
  2099 and failed. The window is inclusive 1970–2069; 2099 is outside it. The digits do not
  take the later century, they take the one century that puts them in range. The spec's own
  examples (`69`→2069, `70`→1970) are both consistent with either reading, so this is the case
  the spec does not disambiguate — a property test now pins every pair of digits against every
  window endpoint.
- **A day label carries no month name in either format.** The table gives `2025-01-31` under
  both `numeric` and `abbreviated`; `2025-Jan-31` appears nowhere. Read as the table's answer
  rather than as an omission, and tested as such.

## Not decided — still yours

- **Gates 0e and 0f** remain unrun; nothing in Phase B touched them.
- **The vectorised decoder** (question 4) is the one deliberate debt. It belongs in this
  package in Phase E, property-tested against the scalar path.
- **`CalendarPoint.sort_key` puts a month-precision point at day zero**, so a month sorts
  ahead of the days inside it. The two never mix within one column, since precision is fixed by
  the column's declared encoding, so the choice only had to be total and stable. If a later
  phase ever mixes precisions in one ordering, revisit this.
- **`UNSPLIT_LABEL = "Data"`** is defined here but unused until Phase C renders names.
