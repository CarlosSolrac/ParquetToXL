## Decisions in Phase H, with the alternatives considered

### 1. What the eight verbs mean

`pqx status|sidecar|plan|write|verify|report|publish|run` is given by the spec as a list of names.
What each name *does* is not, and the list admits two readings.

| Option | What it would mean | Why not |
| --- | --- | --- |
| **Prefix semantics** | Each verb runs the pipeline up to and including its own stage. `write` = stage, describe, plan, write, stop. | Every verb becomes "`run`, but stop here", and `publish` and `run` become the same command under two names. It also makes `verify` need a staged source, when the whole point of the manifest is that it does not. |
| **Durable intermediate state** | Each verb persists its output so the next can resume. | Requires a scratch contract that survives invocations, plus a staleness rule for the intermediate state itself. A second, weaker copy of the problem the receipt already solves. |
| **✅ Distinct jobs** | Three groups: destination-side inspectors, source-side previews, and writers. | Chosen. |

**Chosen: distinct jobs.** It gives each name something only it does, and each group a property
worth stating:

- **Inspectors** — `status`, `verify`, `report` — read the output directory, open no Parquet and
  stage nothing. `verify` is the strongest of the three: it checks a published export against the
  published manifest, reading the dtypes back out of the published sidecars, with the sources
  unreachable. A test deletes both Parquet files before verifying, which is the assertion in its
  strongest form — a `verify` that needed them could not pass.
- **Previews** — `plan`, `write` — publish nothing.
- **Writers** — `sidecar`, `run`, `publish`.

`run` honours selection and is what a scheduler invokes; `publish` is `run --force` under the name
an operator means by it. That is the one pair that overlaps, and deliberately: "rebuild it now" is
a thing people ask for often enough to deserve a verb rather than a flag they have to remember.

### 2. Where a preview's sidecars go — the bug this decision was made to avoid

A preview stages and describes its sources, exactly as a run does. Writing the sidecar to its
**configured** location would leave a mark that says *this source has been described*, which the
next run's selection reads and believes. A command documented as publishing nothing would have
silently skipped the next run's hashing.

| Option | Recommendation |
| --- | --- |
| Write sidecars to the configured location | No. A preview would change what the next run does. |
| Skip describing altogether in a preview | No. The plan depends on the observation; a preview that skipped it would be planning over something other than the data. |
| **✅ Write them into scratch** | Chosen. The preview describes the sources exactly as a run would, into a directory that is deleted when it is done. |

Describing a source into a directory that is about to be removed is not a claim that the source has
been described. `test_plan_does_not_describe_the_sources_where_the_next_run_would_look` asserts it
both ways: no sidecar beside the source, and `status` afterwards still reporting
`sidecar-missing-or-unreadable`.

### 3. `sidecar` as a standalone verb

The spec's negative check asks: *kill a run after sidecars but before the receipt; the next run
rebuilds the export only, not the hashing.* `pqx sidecar` reproduces that state on purpose — it
describes the sources and publishes nothing to the destination.

It must **not** publish sidecars to the destination, which is what the run's `_publish` does later:
the destination would then hold files with no receipt, and the ownership check — correctly — refuses
a directory holding output no receipt accounts for. A `sidecar` verb that published would have
made the next `run` refuse.

### 4. One pipeline body, not two

`plan` and `write` are only worth offering if what they show is what `run` would actually do. Two
implementations of the same sequence would be two things to keep true, and the one that is
exercised less would be the one that drifted.

So `run_profile` and `preview_profile` share `_produce`: stage, describe, arrange, plan, and
optionally write, entirely inside scratch. The difference between them is two arguments — where
sidecars go, and whether to write the workbooks — and everything after that point (verify, publish,
reconcile, report) belongs to `run_profile` alone.

### 5. `argparse`, not a CLI framework

| Option | Why not |
| --- | --- |
| `typer` / `click` | Eight verbs sharing five switches is exactly what `argparse` is for, and a dependency here is one every package in the workspace inherits through `pqx-pipeline`. |
| **✅ `argparse`** | Chosen. Ships typed with the standard library; no stubs to source, nothing to pin. |

### 6. Exit codes

`0` the command did its job and the answer was good; `1` it ran and the answer was bad; `3` it
refused before doing anything; `2` is left to argparse for a usage error. A script can tell "your
export is broken" from "your invocation is broken" without parsing the text.

**Staleness is not a failure.** `status` exits `0` whether or not there is work to do, because
"there is work to do" is the answer it was asked for. Conflating the two would make the obvious
`pqx status && pqx run` wrong in the ordinary case.

**Refusals are per profile.** One destination owned by another configuration does not stop the
profiles that would have succeeded, or fixing a configuration becomes a sequence of runs each
revealing one more problem. The command returns the worst code any profile produced.

### 7. Output through an injected stream rather than `print`

Every verb writes through `Invocation.say`, over a `TextIO` the caller supplies. It makes every
test read a string instead of capturing a file descriptor, and it is also why `ruff`'s `T20` rule
did not have to be suppressed anywhere in the package. The clock is injected the same way, which
is what lets a test assert on a run identifier.

### 8. `excel_record` made public

Finding a sidecar's ToExcel record by identifier — rather than by its position in a list the caller
happened to pass — was private to `staleness`. `verify` needs the same record for the dtypes it
reads fragments back with, and `verify_manifest` takes the schemas as an argument rather than going
looking for the sidecar itself. One implementation, now public, rather than a second search written
against the same fragile assumption.

## ⚠️ What is deliberately not built

### `balanced` planning is not wired into a run

`plan_balanced_sheets` and `minimum_balanced_workbooks` exist and are tested. Nothing yet chooses
between them and the calendar path inside `run_profile`, and a profile that asks for `balanced`
raises by name — `"uses 'balanced', which is planned but not yet wired into a run"` — which the CLI
turns into a per-profile refusal rather than a crash.

Wiring it is not hard; what is missing is a decision the spec does not make. `balanced` has no
period labels, so `naming.worksheet` cannot reference `{period_label}`, and the fan-in ordering
rule ("period first, then source") has no period to order by. Both need an answer before the path
is worth building, and guessing one in code is worse than refusing by name.

### The vectorised date decoder — flagged for the fourth time

`pqx_pipeline.bucketing` decodes one value at a time, so a forty-million-row source pays forty
million Python calls. It is the single call site, so the replacement is a local swap: a Polars
expression built **in `pqx-calendar`, beside the scalar path and property-tested against it** — not
in `pqx-pipeline`, where it would become a second statement of the century-window rule.

This is now load-bearing rather than theoretical: it sits on the run's critical path, between
reading a source and planning it.

### `--dry-run` does not print the delete set

The spec's negative check asks for the delete set under `--dry-run`. It is not there, because
computing it needs the manifest, which needs the plan, which needs the sources staged and read —
the one thing `--dry-run` promises not to do. Printing a delete set that cost a full staging pass
would make the switch mean something other than what it says.

What an operator can do instead is `pqx plan`, which names every workbook a run would produce
without publishing any of them; anything in the destination that is not in that list and not
bookkeeping is what reconciliation would remove. Closing the gap properly means either letting
`--dry-run` stage (and saying so), or having `plan` read the published manifest and subtract —
a small addition, but one that changes what a documented switch means, so it is left as a decision
rather than taken.

### Gates 0e and 0f remain unrun

0e (Spark image, tmpfs sizing) and 0f (Azure round trip) need infrastructure this environment does
not have. Nothing built since assumes an answer from either; both remain yours to run before a
release.

## Verifying it by hand

The spec's end-to-end check, as commands:

```powershell
uv run pqx --config export.json run                 # publishes a verified export
uv run pqx --config export.json status              # says fresh; stages nothing
uv run pqx --config export.json run                 # "nothing was stale; no work was done"
uv run pqx --config export.json verify              # re-checks what is published, opening no Parquet
uv run pqx --config export.json report              # the last run's report, rendered
```

And the negative checks the spec lists, each of which now has a verb:

| Check | Command |
| --- | --- |
| Flip a cell in a published workbook | `pqx verify` → exit `1`, one fragment `digest-mismatch`, its source failing reassembly |
| Change `naming.workbook`, bump T3 | `pqx status` names `config-modified`; `pqx run --dry-run` leaves the destination untouched. See the limitation below: the delete set comes from `pqx plan`, not from `--dry-run`. |
| Change it and **don't** bump T3 | `pqx status` → names `resolved-config-hash`, proving the backstop |
| Restore an older source | `pqx status` → selected, the case a `>` comparison would miss |
| Point a second `config_id` at one directory | `pqx publish` → exit `3` before staging, directory untouched |
| Kill a run after its sidecars | `pqx sidecar` reproduces it; `pqx status` → stale, but no source-level signal |
